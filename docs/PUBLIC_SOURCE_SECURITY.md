# Безопасная публикация исходников DeiLaw

**Цель:** опубликованный исходный код приложения остаётся пригодным для самостоятельной сборки и аудита (GPL-3.0-only), при этом релиз не содержит ключей доступа, пользовательских данных, внутренних отчётов о рабочем окружении или отдельных административных инструментов.

## Что допустимо публиковать

- Клиентские исходники DeiLaw, PyQt6 UI, логику поиска, лицензии, тесты, NSIS/PyInstaller сценарии и воспроизводимые инструкции.
- Исходники Supabase Edge Functions и необходимые SQL-схемы **без настоящих секретов и персональных данных**: безопасность должна обеспечиваться JWT/Auth/RLS/проверкой прав, а не сокрытием исходного кода.
- `SUPABASE_URL`, клиентский **publishable**-ключ и публичный Cloudflare Turnstile *site key* при необходимости: эти значения не являются секретами и в desktop-клиенте всё равно доступны. **Никогда** не публикуйте `service_role`, `sb_secret_...`, Turnstile secret key, OpenAI ключ, токен доступа к БД, приватные ключи обновлений и PFX.

## Что исключено из нового дерева исходников

- Внутренние отчёты о производственном развёртывании, истории оперативных исправлений, результаты проверки live-проекта Supabase.
- Отдельный административный CLI `sync_laws_to_cloud.py`. Он не требуется для работы обычного desktop-клиента.
- Пользовательские БД, репорты/вложения, identity, журналы, backup-архивы, ключи и `.env`; они исключены правилами `.gitignore` и дополнительным fail-closed аудитом.

**Примечание:** исключение документа из текущей ветки Git **не удаляет** его из ранее опубликованной истории GitHub и скачанных старых ZIP-архивов. Если в прошлом действительно был опубликован секрет, немедленно отзовите или смените его. Удаление истории / обращение в GitHub Support — отдельное мероприятие, требующее понимания влияния на форки, теги и подписанные релизы.

## Проверка перед тегом и релизом

1. Запустите `python scripts/audit_public_source.py` в Git-клоне: программа откажет в выпуске при обнаружении определённых внутренних файлов, пользовательских данных или характерных секретов в **отслеживаемом** коде.
2. Запустите `python scripts/verify_source.py` и `python -m unittest discover -s tests -q`.
3. Проверьте, что автоматический Windows CI успешно завершился из **текущей main**, а архив `DeiLaw_Source_v0.3.1.zip` содержит именно файлы соответствующего SHA.
4. Прежде чем предоставлять бинарный EXE, дополнительно выполните аудит лицензий Qt/LGPL, MSVC, исходных кодов DLL и подписи SignPath.

Аудит по шаблонам **не доказывает** отсутствия неизвестных секретов или уязвимостей. SQL-политики и Edge Functions могут быть полностью открыты — надёжная защита данных в работающем проекте Supabase обязательна независимо от состава GitHub ZIP.

Для сообщений об уязвимостях: [SECURITY.md](../SECURITY.md).
