# Бесплатная локальная проверка защиты DeiLaw

**Только тестирование.** Эти действия не обновляют рабочую базу Supabase и
не создают платную ветку. В тестах используются исключительно искусственные
отзывы, репорты, учётные записи и предложения.

## Требуется на Windows

1. Установить и запустить [Docker Desktop](https://docs.docker.com/desktop/).
2. Установить [Supabase CLI](https://supabase.com/docs/guides/local-development/cli/getting-started)
   (достаточно бесплатного локального запуска; не нужно оплачивать Pro).
3. Открыть PowerShell в папке с исходниками DeiLaw, рядом с
   `SUPABASE_SETUP.sql`. Не выполнять `supabase link`, `db push`, `db pull`
   или другие команды, которые могут изменить облачный проект.

**Самый простой запуск:** дважды щёлкнуть `RUN_LOCAL_SECURITY_TEST.bat`.
Скрипт выполнит только локальные команды, а затем попросит вставить локальный
`Publishable` key. Не запускайте его повторно на уже заполненной тестовой
базе: сначала используйте отдельную чистую локальную среду.

Проверьте установленную версию и подсказку команд:

```powershell
supabase --version
supabase db query --help
supabase start
```

`supabase start` создаёт локальные контейнеры: Auth, Postgres, API и Studio.
Запускать следует **только** на компьютере разработчика. Не пробрасывать
локальные порты в интернет: тестовая среда не предназначена для публикации.

## Подготовить тестовую схему

Из корня исходников последовательно:

```powershell
supabase db query --local --file SUPABASE_SETUP.sql
supabase db query --local --file supabase/tests/local_compat.sql
supabase db query --local --file SUPABASE_SECURITY_HARDENING.sql
```

Первый файл воспроизводит историческую схему отзывов и репортов. Второй
создаёт отсутствующие в этом репозитории тестовые структуры админки и
предложений и добавляет фиктивные записи. Третий применяет **настоящую
запланированную** миграцию защиты к этой локальной схеме.

> `local_compat.sql` нельзя выполнять в рабочем облачном проекте.
> Она является тестовым приближением отсутствующей исторической
> миграции админки, а не её заменой для выпуска.

Если CLI не поддерживает `db query --file`, обновите CLI по официальной
инструкции. Не подменяйте `--local` на `--remote`/`--linked`.

## Проверить доступ по JWT

Выполните `supabase status` и скопируйте **локальный** ключ `Publishable`
(или `anon`). Не используйте `service_role`, секретный ключ или ключ
боевого DeiLaw.

```powershell
python scripts/test_local_rls.py
```

Проверка сама создаёт две случайные локальные учётные записи и тестирует:

- попытку чужого пользователя присвоить legacy-данные по установочному ID;
- повторное присвоение уже защищённых данных через другой JWT;
- невозможность читать/редактировать чужие отзывы и репорты;
- невозможность писать в чужую переписку;
- скрытие отзывов до одобрения и блокировку изменения полей модерации;
- отсутствие доступа к чужим предложениям;
- бесполезность подставных заголовков `x-deilaw-installation-*`.

Скрипт **принудительно принимает только** `http://127.0.0.1:54321`
и не сможет отправить тестовые запросы в облачный Supabase.

Если локальные учётные записи не получают JWT сразу после регистрации,
отключите email-confirmation **только в локальном Auth**, затем повторите
тест. На рабочем проекте настройки не менять.

## Дополнительные проверки

```powershell
python scripts/verify_source.py
python -m unittest discover -s tests -v
```

Когда закончите, `supabase stop` остановит локальные службы с сохранением
локальных данных. Не используйте `supabase db reset` вне явно выбранного
локального окружения: эта команда уничтожает данные в целевой базе.

## Границы результата

Успех этого теста **не разрешает** сразу применять миграцию на продакшене:
локальная схема админки имитируется, серверная загрузка вложений и Cloud AI
нуждаются в отдельных контрактных тестах, а старые версии DeiLaw перестанут
работать с новым RLS. Перед публикацией нужны репетиция с точной схемой
продакшена (без пользовательских данных), резервная копия, обновлённый
Windows-клиент и повторная независимая проверка безопасности.
